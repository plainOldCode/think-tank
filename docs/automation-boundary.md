## 0. 한 줄 결론

세 범주 모두 **"기계가 대신할 수 없다"가 아니라 "기계가 손댈 대상이 아니다"**로 수렴한다.
따라서 이 11건을 학습해 probe가 verify하도록 만드는 설계는 **구조적으로 반대 방향**이다 —
학습 데이터가 "자동화가 손대지 않는 케이스"로 100% 구성되므로, 학습된 자동화는
손대지 말아야 할 영역을 집어간다. 이 11건은 학습 데이터가 아니라 **자동화 범위의
경계 정의 데이터**다.

## 2. 유형 정의와 판정

### T1 — 사람 고유 권한 (3건)
에이전트 계약(할 수 있다/없다) 밖의 조직 결정: 임명, 책임 배정, 역할 부여.
대체 불가이므로 자동화 대상이 아니라 **범주 자체가 다르다**.
- 판별: 산출물이 권한 행사 그 자체. 제목에 `[임명]`·`[조직]`, 완료 근거가
  조직 완성·임명 완료.
- 자동화 대체 가능성: **없음.** 자동화는 이 범주를 대행하는 게 아니라
  존재 자체가 권한 침해다.

### T2 — 판단이 산출물 (5건)
에이전트는 실행자이지 최종 판단의 소비자가 아니다. 사람이 읽고 판단하는 것이
**목적 자체**인 작업: 방향 토론, 의견 수렴, 성능 분석, effort 비교, 해결과정 분석.
- 판별: 완료 기준이 "사람이 판단할 재료(문서·분석·요약)"의 산출이고, 후속 조치가
  사람의 결정으로 이어짐(에픽 구성, 상주 결정, 공개 결정 등).
- 자동화 대체 가능성: **없음.** 분석 수행은 에이전트가 할 수 있지만, 그 판단을
  소비하는 주체가 사람이라 자동 종결·자동 verify는 의미를 잃는다.

### T3 — 사람이 직접 수행·결단한 작업 (3건)
에이전트가 못 끝내서 사람이 결단한 게 아니라 **자동화 대상이 아니었던 작업**을
사람이 순차 수행했거나, 사람의 직접 검증(눈으로 확인)으로 종결한 경우.
- 판별: 자동 위임 이력(dispatchs=0) 없이 사람이 직접 claim→수행했거나,
  에이전트 수행 후 사람이 직접 확인하고 승인(M43KDKWQ: 5회 codex dispatch 후
  사람 눈으로 확인).
- 자동화 대체 가능성: **원칙적으로 가능하나 대상 아님.** 이 카드들이 남긴 것은
  "실패 사례"가 아니라 "사람이 선택한 수행 방식"이다.

## 3. 자동화 경계 밖 판정 기준 — probe 참조용 (수용 기준 2)

코드 연결은 별도 카드에서 한다. 본 문서는 probe(및 미래의 자동 verify 확장)가
참조할 기준을 구조화해 선언한다. 아래 술어 중 **하나라도 참**이면 그 카드는
자동화 경계 밖 — 자동 종결·자동 verify·자동 라벨링의 대상에서 제외한다.

```json
{
  "boundary_predicates": [
    {
      "id": "B1",
      "name": "조직결정",
      "rule": "산출물이 에이전트 계약 밖의 권한 행사(임명·책임 배정·역할 부여)",
      "signals": {"title_prefix": ["[임명]", "[조직]"],
                  "evidence_contains": ["임명", "조직"]},
      "effect": "자동화 전면 제외"
    },
    {
      "id": "B2",
      "name": "판단소비",
      "rule": "완료 기준이 사람의 판단·의견 수렴·분석 보고 그 자체이고, 후속 조치가 사람의 결정",
      "signals": {"title_prefix": ["[토론]", "[논의]", "[분석]", "[실험]"]},
      "effect": "자동 verify 금지 — 보고는 사람 소비용"
    },
    {
      "id": "B3",
      "name": "수동수행",
      "rule": "자동 위임 이력 없는 사람 직접 수행(dispatchs=0 + 사람 claim) 또는 사람 직접 검증 종결",
      "signals": {"dispatches_zero_with_manual_claim": true,
                  "evidence_contains": ["사람 승인:", "사람 눈으로 확인"]},
      "effect": "재발령·자동 승격 대상 제외"
    }
  ],
  "input_fields": ["title", "labels", "acceptance", "dispatches",
                    "execution_attempt", "verified_evidence", "comments"],
  "note": "술어는 '하나라도 참이면 경계 밖'. 신규 카드 생성 시점에는 사람이
           경계 밖임을 표시하는 라벨(예: needs-human)을 쓰고, 본 기준은
           사후 분류와 회귀 검증의 참조로 쓴다."

```

주의: 위 신호는 11건에서 관측된 표지일 뿐 완전한 조건이 아니다. `[분석]` 제목이면
무조건 자동화 금지라는 뜻이 아니라, **산출물이 판단 그 자체인지**가 본질이고
표지는 보조 근거다. 오탐 비용(자동화가 손대지 말아야 할 것을 손댐)이
미탐 비용(사람이 직접 승인하는 수고)보다 크다는 판단이 이 기준의 기본값이다.

## 4. attempt 해석 주의 — 작업 회차 ≠ 실패 (수용 기준 3)

- `execution_attempt`는 **작업 회차**다. 실패 횟수가 아니며, 높다고 에이전트가
  못한 것도 아니다. 사람이 직접 claim→구현을 여러 회차에 걸쳐 수행하면
  attempt가 올라간다(M32909TN: 10-10~10-12 걸친 사람 직접 수행 — 본문 분석 시점
  카운트 기준 20회차 언급, 현재 카운터 3).
- M4DF245N(attempt 9 시점 기록)도 이벤트 로그상 제출→[needs-merge]→사람 승인
  1회였다. "에이전트 N회 실패"라는 해석은 데이터가 없다.
- **예산 정책 사각지대 주장도 철회됐다**: budget_reason은 2026-10-09
  (TT 개선#3b) 도입으로 해당 카드 작업보다 먼저 존재했고, claim이 막지 않는
  것은 의도된 설계다 — 자동 수령 풀(pull)을 제한하고 수동 claim은 인간 개입
  경로로 남긴 선택. attempt 상한 강제는 "사람이 카드를 N회 작업한 것"을
  거부하는 셈이라 근거가 없다.
- 따라서 probe·리뷰어는 attempt 숫자를 실패 신호로 읽지 않는다. 회차 해석이
  필요한 판정(예: budget:attempt>=2)은 이미 policy.budget_reason이 담당하며,
  이는 **자동 수령 풀**에만 적용된다(수동 claim 무관).
